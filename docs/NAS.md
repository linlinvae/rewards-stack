# NAS 部署注意事项

[返回首页](../README.md) · [文档目录](README.md)

本仓库使用标准 Docker Compose，不依赖某一台 NAS 的地址、用户名、1Panel 端口或临时 SSH 授权。历史机器专用迁移、授权及热更新脚本只保留在本地，不随仓库公开。

## 新部署

在 NAS 上选择一个新的空目录，放入本仓库公开源码，然后按 [部署说明](DEPLOYMENT.md) 运行初始化、编辑 `.env`、构建及健康检查。`init.sh` 只允许在目标 Linux 主机以 root 初始化，并拒绝覆盖已有 `.env`。

NAS 需要可用的 Docker Compose v2.24+、Bash、Python 3、Git、OpenSSL 等工具。先核对 CPU 架构及基础镜像支持；镜像能拉取不代表浏览器已在该架构验证。面板容器使用 UID/GID 1000，持久化目录权限应按部署文档设置，不要使用 `chmod 777`。

Compose 默认给 Script 0.75 CPU / 768 MiB RAM，给 Dashboard 0.25 CPU / 128 MiB RAM。这是一组示例限制；根据 NAS 可用资源和其他应用负载调整，浏览器资源不足时不能用重复启动任务代替排查。

## 访问面板

默认保留 `127.0.0.1:8890:8890` 绑定，通过 SSH 隧道访问。SSH 用户、主机和非标准端口由部署者自己填写：

```bash
ssh -N -L 8890:127.0.0.1:8890 your-user@your-nas
```

本地访问 [面板](http://127.0.0.1:8890)，使用 NAS `.env` 中的面板凭据。需要浏览器直接访问 NAS 时，建议使用 NAS 自带或自行管理的 HTTPS 反向代理，正确转发鉴权与 SSE；当前预检要求面板监听回环地址。不要直接将未审查的局域网绑定改动当成部署默认，也不要通过公网明文 HTTP 输入密码或验证码。

无需给容器挂载 Docker Socket、使用 privileged，或向运维用户授予任意免密 sudo。本仓库不会添加 SSH 公钥、改写 SSH 服务配置或创建 sudoers 授权。

## 迁移已有数据

1. 在源端关闭计划，确认任务空闲，按部署说明生成一致性备份。
2. 使用可信 SSH/SCP 通道私密传输，校验 SHA256；备份含真实凭据、会话和通知配置，不得放入 Git。
3. 在目标端先检查归档和 SQLite 完整性；保留源端全部数据，目标已有部署也先备份，不能直接覆盖在线数据库或复制活动 WAL。
4. 按部署文档的恢复步骤，在服务停止时建立新目录并恢复权限。目标端使用独立面板密码和 API Token，核对环境变量与镜像版本。
5. 启动后先检查健康、账号、会话元数据、历史与计划关闭状态，再由人工决定登录和任务运行。

跨主机迁移不能保证微软接受原会话。不要为解除错误删除所有会话，也不要自动反复登录。`restore.sh --extract` 仅检查并解出待审查副本，不会替你覆盖在线目录。

## 运维与验证

日常操作使用 `scripts/healthcheck.sh`、`scripts/backup.sh` 及 `scripts/restore.sh`。任何更新前先暂停计划、确认空闲并保留回滚材料。历史升级包与当前源码归档不是同一种安装入口；不要混用。

开发模拟测试见 [docs/TESTING.md](TESTING.md)。Docker 构建、重建持久化、NAS 文件权限、反向代理和真实收件效果须在目标环境分别确认。原始验收报告、截图、服务器信息及面板登录文件不包含在公开仓库。
